# ArcFlare for Android

A thin [Capacitor](https://capacitorjs.com) app that reaches the hub started by `arcflare phone`.
Nothing here is a second hub: the app pairs with your computer, then loads the same phone UI
(`lib/hub/ui`) either straight from the hub on your home network, or from a bundled copy that talks to
the hub through the encrypted relay tunnel (`lib/hub/TUNNEL.md`). The hub itself stays zero-dependency;
this folder has its own `package.json` and lockfile and does not touch the root `package.json`.

**Status: nothing in the native layer has been compiled or run.** The machine this was written on has no
Android SDK (and `dl.google.com` is unreachable), so no APK was built and no emulator or phone was used.
Everything that is plain JavaScript is tested; the rest is listed under
[Unverified on a real device](#unverified-on-a-real-device).

## What it does

1. **First run: pairing.** Run `arcflare phone pair` on the computer, scan the QR it prints with the phone's
   normal camera app. The link `arcflare://pair?...` opens ArcFlare through an intent filter (no camera
   permission, no scanner plugin). Or paste the link into the text box.
2. **The link is validated first**, by the pure module `www/link.js`, before anything is stored or sent
   (version exactly 1, https relay without user info/query/fragment and not an IP address, exact base64url
   shapes for room/hub key/secret, no unknown/duplicate/oversized parts, optional LAN URL only
   `http(s)://<192.168/10/172.16-31 address or name.local>:<port>`). Any problem: a plain message, nothing stored.
3. **Confirmation screen** with the relay host and the hub-key fingerprint (same value `arcflare phone pair`
   prints as "hub key"). Cancel stores nothing. Pair runs `ArcFlareTunnel.pair()` and shows the 6-digit code;
   confirm it **on the computer**. "I confirmed it" checks that the computer approved this phone.
4. **Every launch:** if a LAN URL is stored it is probed for 2 s with `GET /api/status` through Capacitor's native
   HTTP (no CORS, no mixed-content rules). Only a JSON object with a boolean `setup` counts as the hub.
   - LAN answers: the WebView goes to exactly that URL (chip: Home network). **The relay is never used then.**
   - Otherwise the shell opens a relay session once as a check, and if that works starts the bundled UI with
     `window.ArcFlareTransport` set to the tunnel adapter (chip: Relay).
   - Otherwise: "Can't reach your computer" with Retry, Re-pair and Forget this computer.
5. **Forget** wipes the pairing database (and any other IndexedDB of the app), Web Storage, Cache Storage and
   all cookies (via Capacitor's native cookie manager, which also removes HttpOnly cookies) and clears the
   native navigation pin. The computer keeps listing the phone until `arcflare phone devices revoke <id>`.
6. **Getting back to settings.** The hub UI has no settings page, so the shell is a history entry behind it:
   Android Back from the hub's first screen returns to the shell, which then shows a "This computer" screen
   (Open / Re-pair / Forget) instead of jumping forward again.

## Layout

```
android/
  package.json, package-lock.json   exact pins: @capacitor/core, cli, android 8.5.3; app 8.1.2
  capacitor.config.json
  www/                  the web app Capacitor ships
    index.html shell.js shell.css      shell screens (pairing, confirm, code, unreachable, forget)
    link.js               PURE link validator            mode.js        PURE mode decision + LAN probe
    fingerprint.js        hub-key fingerprint            store.js       IndexedDB pairing record + wipe
    transport.js          tunnel -> ArcFlareTransport    native.js      Capacitor bridge wrappers
    relay-boot.js relay-chip.js        run in the bundled UI page
    ui/  vendor/          GENERATED by scripts/sync-ui.js, never committed
  scripts/sync-ui.js      copies lib/hub/ui to www/ui, builds the relay-mode index.html, copies Capacitor's runtime
  android/                the native Android project (generated by `npx cap add android`, then hardened)
  test/                   node:test tests + Playwright shell.e2e.js
```

## Build

### CI (the supported way)

`.github/workflows/android.yml` (ubuntu-latest, JDK 21, Node 22): `npm ci`, `npm test`, `sync-ui`,
`npx cap sync android`, `./gradlew assembleDebug` always, `assembleRelease` only when signing secrets exist.
Both APKs are uploaded as artifacts. The job has `permissions: contents: read`, uses no `pull_request_target`,
and hands secrets only to the steps that need them.

Release signing secrets (repository settings, Actions secrets): `ANDROID_KEYSTORE_BASE64`
(`base64 -w0 release.jks`), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.
The keystore is decoded to the runner's temp dir, deleted at the end, and never written to the repo.

Actions are pinned by **exact version tag, not commit SHA** (the SHAs could not be looked up offline and are
not written from memory). Pin them to SHAs before relying on releases.

### Locally (needs the Android SDK, JDK 21)

```
cd android
npm ci
node scripts/sync-ui.js          # or: npm run sync-ui
npx cap sync android
cd android && ./gradlew assembleDebug      # app/build/outputs/apk/debug/app-debug.apk
```

Release signing locally: export `ARCFLARE_KEYSTORE` (path), `ARCFLARE_KEYSTORE_PASSWORD`,
`ARCFLARE_KEY_ALIAS`, `ARCFLARE_KEY_PASSWORD`, then `./gradlew assembleRelease`. Without them no signing
config exists and the release build is unsigned (not installable).

### Tests (run anywhere with Node 22)

```
npm test            # node:test: link, mode, fingerprint, transport, hygiene and native-config lint
npm run test:e2e    # Playwright + Chromium with a fake Capacitor bridge and fake tunnel (skips if absent)
```

## Install the APK

Download `arcflare-release-apk` (or `arcflare-debug-apk`) from the workflow run's artifacts, unzip, copy the
`.apk` to the phone and open it (allow "install unknown apps" for your file manager or browser once), or with
USB debugging on: `adb install app-release.apk`. Requirements: Android 8.0+ (minSdk 26) and
**Android System WebView / Chrome 133 or newer** (WebCrypto X25519). The app checks this before pairing and
says so if the WebView is too old; it never falls back to a weaker scheme. Debug builds are signed with the
debug key and are for testing only.

## Security design

- **Pairing secret.** `ps` exists only in the pasted/launch link, in a local variable until `pair()` finishes or the
  person cancels. It is never stored, logged or put in a URL; the paste box is cleared on submit and the clipboard is
  overwritten with an empty string (best effort). `pair()` receives a re-built canonical link made from the values
  `link.js` accepted, not the raw text. The LAN URL kept is the one `link.js` accepted, not whatever the tunnel client
  parsed. `loggingBehavior` is `none`.
- **Where things live.** `tunnel-client.js` itself stores nothing (checked by a test). The shell keeps one record in
  IndexedDB (`arcflare-pairing`): relay, room, hub key, device id, room token, label, LAN URL and the device key,
  which the tunnel client generates **non-extractable** (script can use it, not read it out). No `localStorage`,
  `sessionStorage`, cookies, URLs or logs: `test/hygiene.test.js` scans the shell sources and fails on any of them.
  Android backup is off (below).
- **Hub key pinned**, fingerprint shown before pairing; SAS code shown after; approval only at the computer's keyboard
  (TUNNEL.md 5.3). A relay answering with another key fails the handshake.
- **Stolen phone, revocation.** `arcflare phone devices revoke <id>` on the computer cuts the phone off (TUNNEL.md 10);
  the phone then sees "The relay no longer accepts this phone". The session cookie never reaches the phone in relay mode.
- **No downgrade.** Links with `v` other than 1 are refused; there is one suite (TUNNEL.md 11).
- **CSP on bundled pages** (meta tag, because bundled files have no headers):
  `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self' https:; base-uri 'none'; form-action 'none'`.
  **Tradeoff of `connect-src https:`:** the relay is a user-configurable host (`arcflare phone relay on <url>`), so the
  policy cannot name it. It means a script that ever ran in the page could talk to any https host. It cannot get at the
  device key (non-extractable) or the cookie (kept on the hub), and nothing but our own files may run (`script-src 'self'`,
  no inline script). Tightening it to one host is possible if you only use one relay: edit the CSP in `www/index.html` and
  `scripts/sync-ui.js`. The hub's own page, loaded in LAN mode, keeps the hub's stricter `connect-src 'self'`.
- **Native hardening** (all in `android/app/src/main`, each line commented): `allowBackup=false` plus
  `dataExtractionRules`/`fullBackupContent` excluding every domain; release `debuggable false`; WebView debugging off in
  every build (`webContentsDebuggingEnabled:false`, so debug builds cannot be inspected with chrome://inspect either);
  `allowFileAccess`/`allowContentAccess` off; only the launcher activity is exported, the template FileProvider is removed,
  the only permission is INTERNET; the intent filter is `arcflare://pair` only (no https app links); `FLAG_SECURE`
  (no screenshots, blank recents thumbnail); system CAs only; minSdk 26.
- **Cleartext and the navigation pin.** The user's LAN hub is plain http on a private address that cannot be listed in a
  network security config, so cleartext is allowed app-wide. What limits it: `MainActivity` replaces the WebView client and
  refuses every top-level navigation except `https://localhost` (the bundled app) and the *exact* scheme+host+port stored as
  the LAN URL; everything else is dropped and **opens nothing** (no browser). The stored origin is held in memory by a small
  Capacitor plugin (`NavGuardPlugin`, reached only over Capacitor's own bridge); the shell sets it on each launch after a
  successful probe and clears it in relay mode and on Forget. The plugin refuses to be called unless the page is the bundled
  one and the URL has a private-looking shape. Capacitor's bridge is only exposed to the bundled origin (Capacitor registers
  its message listener for `https://localhost` only), so a LAN page cannot call it.
- **The LAN path is unchanged** (TUNNEL.md 1): plain http on a trusted Wi-Fi, or the hub's own `--cert/--key`. Anyone on
  that Wi-Fi can see that traffic; use the relay or a certificate if you do not trust the network.

### Residual risks (read with TUNNEL.md section 14)

- A malicious app build or compromised WebView defeats everything on the phone side. Only install builds you made.
- Capacitor's built-in `CapacitorHttp` and `CapacitorCookies` plugins add `addJavascriptInterface` objects
  (`CapacitorHttpAndroidInterface`, `CapacitorCookiesAndroidInterface`) to the WebView; they cannot be removed without
  patching Capacitor. Both are disabled in config (no `fetch` patching), but the objects are present for any page loaded in
  the WebView, including the hub's own page in LAN mode. We add no JavaScript interface ourselves.
- On a WebView without `WEB_MESSAGE_LISTENER` support, Capacitor falls back to exposing `androidBridge` to every origin.
  The relay needs WebView 133+, which has it, but LAN mode on an older WebView would not.
- LAN mode loads whatever answers at the stored address and passes the `setup` check. That is the hub the user paired with,
  but anyone who can take over that IP on your Wi-Fi can serve a page there. The relay path has no such weakness (pinned key).
- Pairing links can reappear: if Android restores the task from recents with the original VIEW intent, the shell shows the
  confirmation screen for the old link. It is harmless (the link is one-time and expires after 10 minutes) but confusing.
- The relay is checked with a real handshake at launch, then closed; the bundled UI opens its own session. That is one extra
  handshake per launch in relay mode (well inside the hub's 60/min limit).
- Launcher icons are the panda on a dark tile, generated once with PIL, not designed icons.

## Contract notes (UI agent, `window.ArcFlareTransport`)

The adapter (`www/transport.js`) is built on `Tunnel.request()` / `Tunnel.eventSource()` and does not modify
`tunnel-client.js`:

- `fetch` returns `{ok, status, statusText, headers.get(), json(), text()}`; it does not use `tunnel.fetch()` so it never
  depends on a global `Response`. Only Accept, Content-Type and X-CSRF-Token are passed on; `credentials` is ignored.
  Paths must start with a single `/`.
- `tunnel.eventSource` has **no `addEventListener`**: the wrapper adds `addEventListener`/`removeEventListener`. Unnamed
  events reach `onmessage` and "message" listeners. tunnel-client only ever emits unnamed events, so listeners for named
  types are accepted and never fire (the hub sends only unnamed events). A stream whose session is unavailable gets one
  asynchronous `onerror` and `readyState 2`; **there is no retry in the adapter**, the UI does `/api/me` and backoff.
- The session opens lazily on first use, concurrent calls share one connect, and after `onclose` the next call opens a
  new one. A GET/HEAD that hits a just-closed session reconnects once; a POST is never retried.
- tunnel-client's `Mailbox` rejects with `PENDING`, `OFFLINE`, `REFUSED`, `TIMEOUT`, `HANDSHAKE`; the shell turns these
  into plain sentences.

## Unverified on a real device

Nothing below was compiled or executed. Check each on a real phone (Android 8+ with WebView 133+):

1. **The whole Gradle/AGP build.** The project is the unmodified `npx cap add android` output (Capacitor 8.5.3, AGP 8.13,
   Gradle 8.14.3 wrapper, compileSdk/targetSdk 36 = the Capacitor default) plus the changes below.
2. `variables.gradle`: `minSdkVersion` 24 -> **26**.
3. `app/build.gradle`: `debuggable false` in `release`; optional `signingConfigs.release` read from `ARCFLARE_*` env vars.
4. `AndroidManifest.xml`: `allowBackup="false"`, `dataExtractionRules`, `fullBackupContent`, `networkSecurityConfig`;
   second intent filter on `MainActivity` for `arcflare://pair` (VIEW/DEFAULT/BROWSABLE, no `autoVerify`); FileProvider and
   `file_paths.xml` **removed** (check nothing in Capacitor needs it at build time).
5. `res/xml/network_security_config.xml` (cleartext allowed, system CAs only), `data_extraction_rules.xml`, `backup_rules.xml`
   (the `<exclude domain="...">` lists are accepted by the Android 12+ and <=11 parsers).
6. `MainActivity.java`: `registerPlugin(NavGuardPlugin.class)` before `super.onCreate`; `FLAG_SECURE`; `setAllowFileAccess(false)`
   and `setAllowContentAccess(false)` on the bridge's WebView; `bridge.setWebViewClient(new GuardedClient(bridge))` after
   `super.onCreate`. **Verify** that the replacement client does not break Capacitor's asset serving at `https://localhost`
   and that the first page load is not blocked, and that both `shouldOverrideUrlLoading` overloads compile.
7. `NavGuardPlugin.java`: `@CapacitorPlugin` with one method; it uses `getActivity().runOnUiThread` and
   `getBridge().getWebView().getUrl()`. **Verify** `Capacitor.registerPlugin("NavGuard")` finds it (it is called through
   `window.Capacitor` from `www/native.js`) and that `getUrl()` equals `https://localhost/...` when the shell calls it.
8. **Navigation pin behaviour.** That `location.assign("http://192.168.x.x:port")` from the shell reaches
   `shouldOverrideUrlLoading` and is allowed after `setLan`, that any other target (redirect from the hub, link, `window.open`)
   is refused and opens nothing, and that cleartext http to the LAN works from the WebView.
9. **Deep links:** scanning the QR with the stock camera app opens ArcFlare; cold start uses `App.getLaunchUrl()`, warm start
   `appUrlOpen`; the camera app/Google Lens might show the link as text to tap rather than open it directly.
10. **`App.getLaunchUrl()` after Back:** the shell skips the launch URL when the page was reached by history Back
   (`navigation.type === "back_forward"`); confirm Android's WebView reports that.
11. **Capacitor injection under the CSP:** the bridge is injected as a document-start script (WebView 133+ supports it). On
    the old fallback (inline `<script>`) the CSP would block it.
12. **Capacitor `CapacitorHttp.get` options** `disableRedirects` and `connectTimeout`/`readTimeout` honoured, and
    `responseType: "json"` yields a parsed object for the hub's `/api/status`.
13. **`CapacitorCookies.clearAllCookies`** really removes the hub's HttpOnly session cookie for the LAN origin even with
    `plugins.CapacitorCookies.enabled: false` (that flag only turns off `document.cookie` patching in the sources read).
14. **WebCrypto X25519 inside the real WebView**, IndexedDB persistence of the non-extractable `CryptoKey` across app restarts and
    updates, and that Android auto-backup/device transfer really exclude it.
15. **FLAG_SECURE** hides the password screen in screenshots and recents; `webContentsDebuggingEnabled:false` in debug and release.
16. **Install and signing:** the release APK signs and installs; icons render (generated, not designed).

## What the tests cover (and not)

146 `node:test` tests (link validation incl. 89 rejected inputs, mode decision, fingerprint vs the CLI's own function,
transport adapter against a fake tunnel and against the real tunnel-client's closed-session behaviour, storage hygiene,
native-config lint) and 16 Playwright checks of the shell with a fake bridge. They prove the JavaScript logic and that the
native files say what they should; they cannot prove that Android accepts them.
